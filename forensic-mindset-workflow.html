Forensic Mindset and Workflow

Preserve everything. Change nothing.

That is the whole job in two sentences. Everything else in this article is just how you stay true to it when a machine is on fire and everyone wants answers yesterday.

Forensics is mostly simple OS and networking, done carefully. The tools are the easy part. The hard part is staying calm, staying methodical, and not fooling yourself.

The mindset

  • Preserve first, investigate second. Evidence you alter is evidence you may lose.
  • Work on a copy. Examine the working image, never the original.
  • Think in timelines. Almost every case reduces to "what happened, in what order?"
  • Rule things out. Chip away everything that doesn't look like an elephant. Figure out all the ways it didn't happen.
  • You will always leave a footprint. Locard's exchange principle cuts both ways: the attacker leaves dots, and so do you. Minimise your own system modification and write down what you touched.
  • Evidence is not evident. It needs context before it means anything.

Blue team's edge is simple. Every time red interacts with a target it leaves a dot, and blue can connect the dots before red knows it.

The scene comes first

Before any tool, look at the machine. Feel the chassis for heat. Check the LEDs. Photograph the scene immediately.

  • Keep the session alive. Don't lock it, don't log out.
  • Isolate the network (pull the cable or cut the switch port) so nothing more leaves. Containment should follow from the evidence, not from panic.
  • Volatile data disappears first, so dump memory before you power anything down.
  • Communicate out of band. If the attacker is in the mail system, don't plan the response over email.
  • If the machine hibernated, RAM was written to hiberfil.sys. For a VM, suspend it and grab the .vmem file.

Memory capture on Windows: FTK Imager, WinPMem, DumpIt, Magnet RAM Capture.

winpmem_mini_x64.exe C:\evidence\mem.raw

Disk next. Image it, hash it, and only ever mount the image read-only.

sudo dc3dd if=/dev/sdb of=evidence.dd hash=sha256 log=acquisition.log
sha256sum evidence.dd
mmls evidence.dd                 # find the partition offset
fls -r -o 2048 evidence.dd       # list files, deleted ones marked with *

The workflow

This is the loop I want to become second nature:

identify, static, unpack, dynamic, deep dive, memory, extract IOCs, turn them into detections.

Start with one known indicator and pull on that thread. A hash, a domain or an IP is enough to begin.

1. Identify and fingerprint

Same input always gives the same hash. Change one bit and the output changes completely (the avalanche effect), and you can't work backwards from a hash to the data. A hash is a fingerprint. Use it to track a sample, confirm you've seen it before, and share it as an IoC.

file sample.exe                  # extension spoofing shows up here
sha256sum sample.exe
Get-FileHash -Algorithm SHA256 .\sample.exe     # on Windows
hexdump -C sample.exe | head

Attackers can change a file hash with a tiny modification, so go fuzzier:

ssdeep -pb *                     # fuzzy hashing (CTPH), match similar files
python3 -c "import pefile; print(pefile.PE('sample.exe').get_imphash())"

Masquerading and extension tricks map to MITRE ATT&CK T1036.

2. Static analysis

No execution yet. Look at strings, imports, exports and sections. You're hunting for embedded filenames, IPs and domains, registry paths, Windows API names and command-line arguments.

strings -a sample.exe | less
floss sample.exe                 # recovers obfuscated strings

3. Unpack

If the strings look like junk and the imports are tiny, it's probably packed (T1027.002). UPX is the common one.

upx -d -o unpacked.exe sample.exe
strings -a unpacked.exe | less

4. Dynamic analysis

Now run it, but only in an isolated lab VM. Sysmon sits at the centre of this: it records process creation, network connections and file writes. Add Process Monitor and Wireshark.

Traffic analysis belongs here. My lesson learnt: always inspect the network traffic.

5. Deep dive

When behaviour isn't enough, open it in a disassembler (Ghidra, Cutter, IDA) or step through it in a debugger like x64dbg. Understanding the PE format and its sections pays off here, and so does knowing how a call travels from user mode through NTDLL.DLL into the kernel. Malware often tries to climb from user mode to kernel mode.

Memory forensics

Memory is the live state of the machine at one moment: processes, network connections, loaded DLLs, handles, command history, credentials, injected code.

I think of it like a privilege escalation, only blind. You are looking around a system you can't touch, through a snapshot.

The SANS approach, in order:

  • Identify and verify processes (look for odd names and wrong parents)
  • Dig into DLLs and handles
  • Review network activity
  • Hunt for code injection (T1055, including process hollowing T1055.012)
  • Look for rootkits (T1014)
  • Dump the suspicious pieces for further analysis
vol -f mem.vmem windows.info
vol -f mem.vmem windows.pslist
vol -f mem.vmem windows.pstree               # find the parent process
vol -f mem.vmem windows.cmdline
vol -f mem.vmem windows.netscan
vol -f mem.vmem windows.malfind              # injected code
vol -f mem.vmem windows.dlllist --pid 1234
vol -f mem.vmem windows.svcscan
vol -f mem.vmem windows.registry.hivelist

Volatility 3 doesn't need a profile like version 2 did. windows.info works it out.

The low-tech trick still works too: dump the memory image to text and grep it.

strings -a mem.vmem > mem.txt
strings -a -el mem.vmem >> mem.txt        # UTF-16 strings
grep -i "powershell" mem.txt

Windows artefacts: where it leaves dots

This is where the timeline gets built. Two groups matter most.

Execution artefacts tell you what ran:

  • Prefetch: C:\Windows\Prefetch
  • Shimcache: HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\AppCompatCache
  • Amcache: C:\Windows\AppCompat\Programs\Amcache.hve
  • UserAssist and RunMRU in the user's registry hive
  • Jump Lists, LNK files, Recent Items
  • Event logs: C:\Windows\System32\winevt\Logs
  • SRUM database: C:\Windows\System32\sru

Persistence artefacts tell you how it stays:

  • Run and RunOnce keys, Winlogon keys, Startup folders (T1547.001)
  • Scheduled tasks in C:\Windows\System32\Tasks (T1053.005)
  • Services in HKLM\System\CurrentControlSet\Services (T1543.003)
reg query HKCU\Software\Microsoft\Windows\CurrentVersion\Run
reg query HKLM\Software\Microsoft\Windows\CurrentVersion\Run
schtasks /query /fo LIST /v
autorunsc.exe -a * -c > autoruns.csv            # Sysinternals

Rapid collection is KAPE's job, and Zimmerman's tools parse what it collects:

kape.exe --tsource C: --tdest D:\out --target !SANS_Triage
PECmd.exe -d D:\out\C\Windows\Prefetch --csv D:\out\parsed

Don't forget the quiet places: the Recycle Bin, alternate data streams (T1564.004), shadow copies, and cleared logs (T1070.001). Deleted things often aren't gone.

Then stitch everything together:

log2timeline.py --storage-file timeline.plaso evidence.dd
psort.py -o l2tcsv -w timeline.csv timeline.plaso

Think like the other side

A competent attacker doesn't talk to the victim from their own machine. Expect cheap disposable VPS boxes, compromised sites as redirectors, a command server hidden behind them, staging kept separate from exfiltration, and fast flux DNS (T1568.001). C2 traffic itself falls under T1071.

That's why a single IP rarely tells the story. Follow the pattern instead.

Turn findings into detections

The investigation isn't finished until it makes the next one easier. Every IoC should become a detection. Ask: what's the signature?

rule Suspect_Sample_01
{
    strings:
        $c2 = "c2.example.com" ascii wide
    condition:
        uint16(0) == 0x5A4D and $c2
}

Run it with yara -r rule.yar /path/to/scan. YARA was created by Victor Alvarez at VirusTotal.

The psychology bit

Your own brain is the weakest tool in the kit.

  • Confirmation bias: you form a theory in the first ten minutes and start collecting only what supports it. Try to break your own theory. That's the rule-out mindset.
  • Anchoring: starting with one known indicator is useful, but don't let it become the whole case.
  • Urgency: the urge to act is strongest right when you should be most careful. Preserve first.
  • Hindsight: everything looks obvious once you know the ending. Write down what you knew at each step, so the report stays honest.

Risk means more things can happen than will. Your job is to explain the past, and the only way to do that reliably is to rule out the alternatives.

Back to the core

Again and again the work returns to the same fundamentals: how the OS works and how networks talk. Sysinternals sits right at the front of that, so I'm building my toolkit around it.

The current is deep, but the method is simple. Preserve, copy, timeline, rule out, repeat.
